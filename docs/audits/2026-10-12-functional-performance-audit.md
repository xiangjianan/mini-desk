# Mini Desk 功能与性能检查

日期：2026-10-12。检查基线：`cc3098c`（1.1.0）。本次只检查和记录，不修改产品行为。

## 范围与验证

围绕 `src/App.vue`、状态/存储辅助函数、composables、主要交互组件和 `server/` 中继，检查了编辑、保存、撤销、图片处理、工作空间切换、跨标签同步、提醒、手机速记和导入清空的调用路径。没有对宣传视频项目做功能审计，也没有连接生产服务或读取用户真实浏览器数据。

- 前端现有测试：69 个文件、1662 条测试通过。
- TypeScript 检查与生产构建通过。构建提示 `advancedChunks` 已弃用，Naive UI 分包约 621KB（gzip 166KB）；这是构建/首屏优化线索，不代表业务错误。
- 临时 Vitest 探针：8 项检查通过，其中 6 项复现功能或重复保存问题，1 项验证每次输入生成全量快照，1 项测量快照开销。探针按当前错误行为断言，用于审计取证，检查后移除，避免把错误行为固化成正式测试契约。
- 服务端测试未能运行：当前 Python 环境缺少 Flask，收集阶段失败。因此服务端结论来自代码路径分析，未做真实 MySQL/网络故障验证。
- 完整前端测试期间出现一次 ResizeObserver/jsdom 的 `global.removeEventListener` 异常输出，但测试汇总全部通过；该输出不作为生产功能 bug 的证据。
- 本次没有做真机浏览器性能录制。以下性能数字为本地 jsdom/Node 模拟，不能直接当作所有设备上的帧率结果。

优先级：P1 表示可能覆盖或丢失数据，应优先修复；P2 表示交互正确性或明显扩展性问题；P3 表示可以随后处理的额外开销。

## 功能问题

### F1 · P1 · 跨标签页同步等待图片期间会覆盖本地新输入【已复现】

位置：`src/App.vue:1471`，尤其 `1483–1487`。

`applyExternalStoredState` 只在进入时检查是否有本地未保存修改、远端版本是否更新。随后等待 IndexedDB 图片水合；等待结束后只检查组件是否还挂载，直接整体替换状态并重置编辑基线。

触发：标签 B 收到标签 A 的保存事件 → B 等待图片读取 → 用户在 B 输入文字 → 图片读取完成。B 的新输入被远端状态覆盖，并被标记为没有待保存编辑。探针把水合 Promise 挂起，期间输入 `typed-during-hydration`，恢复 Promise 后确认内容变为 `remote`、`hasPendingEdits()` 为 false。

同一缺口也允许两个远端版本的水合以相反顺序完成，较旧结果可能覆盖较新结果。

建议：异步读取前捕获本地编辑代次和状态版本，提交前再次核验；对远端采纳建立请求序号，拒绝过期结果。不要用重置基线掩盖在途新编辑。

### F2 · P1 · 图片冲突合并只更新本地图片，却采纳整板最新版本号【已复现】

位置：`src/composables/useBoardPersistence.ts:136`；`src/App.vue:1318`、`src/App.vue:194`；存储合并在 `src/state/storage/persist.ts`。

图片 scope 的冲突合并以最新持久化整板为底，因此磁盘上会保留另一标签页的文字修改。但调用者只把合并图片和 `sync` 更新到内存，其他字段仍然是旧值。下一次全量保存时，版本检查因本地已经采纳最新 revision 而放行，把旧文字重新写回。

触发：B 持有旧状态；A 修改便签并保存；B 添加图片触发图片合并；B 再执行任意全量保存。探针确认第一次合并后磁盘保留 `remote-only-edit`，本地内存没有该内容，第二次保存后磁盘上的该修改也消失。

图片替换使用独立保存路径，存在同类问题。若本地仍有待保存文本，还需要明确处理文本合并/冲突，不能只更新版本号并把文本代次视为已保存。

建议：成功合并后，以完整合并结果作为新基线，保留已水合的图片原文；本地未落盘修改应显式重放或维持冲突状态。

### F3 · P1 · 手机队列在桌面确认保存前被标记消费【代码推导】

位置：`server/app.py:359`、`src/sync/inboxClient.ts:68`、`src/App.vue:1090`。

服务端 GET 在返回 HTTP 响应前就提交 `read_at`，下次不再返回这些条目。客户端需要随后解析、解码、应用补丁并保存；没有持久化成功后的确认协议。

触发：服务端已提交消费标记，但响应丢失/客户端超时；或者桌面拉取后关闭页面、解码失败、保存冲突、localStorage 写入失败。客户端没成功保存，下一轮 GET 也拿不到记录。`pullInboxes` 还忽略 `persistNow()` 的 false 返回值，仍可能提示已收到并返回 `applied`。

建议：改为可重试读取或有期限的领取，客户端持久化成功后按服务端条目 ID 确认；本地保留导入 ID 做去重。不能仅靠“GET 只读一次”保证可靠投递。

### F4 · P1 · 手机显示发送成功时，服务端尚未可靠入库【代码推导】

位置：`server/app.py:54`、`server/app.py:98`、`server/app.py:340`；手机成功清空草稿在 `src/components/MobileInboxCapture.vue:193`。

POST 启动 daemon 线程后立刻返回成功。即使关闭 AI 润色，也通过后台线程入库。数据库失败仅打印日志；进程重启也可能终止线程。手机拿到成功响应后清空原文，用户没有重试依据。

建议：先可靠存入数据库或持久化任务队列再响应成功，润色作为后续处理；入库失败返回可重试错误。客户端重试应复用同一个请求 ID。

### F5 · P2 · 仅按毫秒时间戳去重会过滤从未导入的新条目【已复现】

位置：`src/sync/pull.ts:100`、`src/sync/pull.ts:103`、`src/App.vue:1101`；服务端时间戳生成在 `server/app.py:107`。

客户端跳过所有 `createdAt <= lastSeenAt` 的记录。但时间戳不是唯一顺序号：两个后台任务可能同毫秒生成时间戳，在不同事务中先后提交；服务端在打开连接和提交前已经生成时间戳，较早时间戳也可能较晚可见。

触发：第一批推进水位线至 T；第二批返回一个新 ID，但时间为 T 或小于 T。探针提供一个从未见过的 ID、时间等于水位线，确认结果没有补丁。结合读即消费，该条目也不再重试。

建议：采用服务端可靠序列/投递 ID 和客户端 ID 去重，允许提交乱序；不能只把比较运算改为 `<`，那会引入重复且仍不能处理乱序。

### F6 · P2 · 图片仍在撤销历史中，删除五秒后却无法恢复【已复现】

位置：`src/App.vue:1396`、`src/App.vue:1383`；`src/composables/useUndoHistory.ts:88`。

通用清理会保留撤销快照引用的载荷，但专门的五秒删除计时器仅检查当前工作空间/待办是否引用它，忽略撤销历史。之后撤销时，无法水合的图片被过滤掉，因此撤销记录存在，图片却无法恢复。

探针确认撤销栈最后一项仍含图片 ID；推进五秒后撤销，图片列表仍为空。专注图片的删除和旧版本清理也使用这一计时器。

代码明确设计了五秒宽限，因此应确认产品是否刻意仅允许五秒内恢复图片。如果保留当前规则，需要同时移除/标明失效的撤销项；现在的通用历史与载荷保留策略不一致。

建议：统一载荷引用判断，包含历史、当前状态和权威存储；或把五秒恢复限制明确体现在交互与撤销行为中。

### F7 · P1 · localStorage 写入失败会抛出，并使保存状态停在“保存中”【已复现】

位置：`src/composables/useBoardPersistence.ts:109`、`src/composables/useBoardPersistence.ts:123`；写入在 `src/state/storage/persist.ts:109`。

保存管线对版本冲突做了处理，但没有捕获存储配额/访问错误。`markSaving()` 已经执行，后续异常跳过恢复 dirty 状态和失败提示。防抖路径还通过 `void` 调用异步保存，可能形成未处理的 Promise rejection。

探针令 `Storage.setItem` 抛出 `QuotaExceededError`，确认异常外抛、保存状态仍为 `saving`。用户可能继续编辑并在离开后丢失尚未落盘的内容；快捷按钮执行等“先保存再执行”的路径也可能被中断。

建议：保存层统一捕获异常，保留编辑代次和可重试状态，给出中英文失败反馈；只有真正成功后更新保存基线与广播。

### F8 · P2 · 异步新增图片的落点随当前工作空间漂移【代码推导】

位置：`src/App.vue:1711`，尤其 `1725`、`1743`、`1768`；`src/App.vue:911`。

新增图片经历文件读取、尺寸读取和 IndexedDB 写入，却不捕获入口时的工作空间 ID。完成后 `insertStoredImage` 直接使用当时的 `activeWorkspace`。`shouldBlockBoardEffects` 仅判断移动端拦截，不能判断空间是否变更。

触发：在 A 上传/粘贴较大的图片，读取期间切到 B；图片最后插入 B。专注图片落点只有 period/id，没有 workspaceId；导入复制产生重复任务 ID 时也可能误命中。快速连续切换空间自身还缺少在途请求顺序保护，较慢的早期切换可能最后生效。

建议：捕获并携带 workspaceId，完成后按稳定 ID 查找原目标并确认目标仍有效；空间切换使用请求序号。

## 性能问题

### C1 · P2 · 输入防抖未覆盖全量快照，每个按键仍遍历所有工作空间【已验证并测量】

位置：`src/App.vue:757`、`src/App.vue:2786`；`src/composables/useBoardPersistence.ts:150`；`src/composables/useUndoHistory.ts:42`；`src/state/todos.ts:64`。

便签/待办编辑 → `markDirty` → `recordUndoCheckpoint` → 全板复制、JSON.stringify、JSON.parse 并提取图片 ID。三秒/一秒防抖只延迟写盘，没有延迟这一同步工作。待办修改还先复制当前空间的所有清单和任务对象。

探针连续输入十次、未触发保存计时器，仍产生十次 stringify 和十个全板历史快照。

模拟条件：Vue reactive 状态；一个空间，1000/10000 条待办，每条约 80 个中文字符；只更改一行便签；每组五次 checkpoint 均值。

| 总待办数 | 单次 checkpoint 均值 | 快照字符串长度（UTF-16 code units） |
| --- | ---: | ---: |
| 1000 | 2.41ms | 117814 |
| 10000 | 20.01ms | 1179814 |

20ms 已超过 60Hz 的一帧预算，且尚未包含真实浏览器布局/绘制和组件更新。普通小看板不一定卡顿；增长后开销来自全板总量，而非正在编辑的那一项。

建议：按编辑事务合并历史，考虑字段/工作空间增量快照，避免每次按键 stringify+parse 整板；待办辅助函数只复制目标清单和被修改对象。

### C2 · P2 · 图片替换直接追加撤销记录，绕过 50 条/8MB 上限【代码推导】

位置：`src/App.vue:1323`；正规裁剪逻辑在 `src/composables/useUndoHistory.ts:63`。

`persistImageReplacement` 直接向 `undoSnapshots` 追加 `previousSnapshot`，没有调用历史数量和体积裁剪。持续编辑/替换图片且中途没有其他普通 checkpoint 时，历史可以无限增长；图片引用保留集合也随之增长。

此外预算以 `string.length` 计数，并非准确字节数，且未计入 `lastUndoSnapshot` 和 Set 开销。即使普通路径限制生效，也不能声称真实内存严格小于 8MB。

建议：所有路径经统一 enqueue/cap 接口；按近似实际字符串内存或明确的字符预算计量，包含基线快照。

### C3 · P2 · 图片清理游标仍读取所有完整图片载荷【代码推导】

位置：`src/state/images.ts:117`、`src/state/images.ts:137`；`src/composables/useBoardPersistence.ts:145`。

代码注释写“只收集元数据”，但实际 `openCursor()` 读取同一个对象仓库的完整 value，包含大体积 `src`。没有 getAll 降低了同时驻留的峰值，仍然有全部载荷的读取/结构化克隆成本。多数非 text 保存都会在 500ms 后触发整库扫描，包括与图片无关的设置、快捷按钮点击、专注 checkpoint。

建议：把元数据和原文分仓库，或使用能在不读取原文时枚举的索引/键；仅在图片变更或闲时批量清理。验证时使用真实 IndexedDB 的大图集合记录读取量和保存后的长任务。

### C4 · P2 · 大图画笔每次移动复制全部点并重绘原图和所有指令【代码推导】

位置：`src/components/ImageEditor.vue:153`、`src/components/ImageEditor.vue:231`、`src/components/ImageEditor.vue:425`。

每个画笔 pointermove 都展开整个 points 数组；深层 watch 又遍历变化并触发整张原分辨率 canvas 清空、drawImage、所有历史指令重绘。长笔画的累计点复制接近二次增长，高分辨率图片会放大重绘成本。当前没有每帧合并或编辑用缩小画布。

建议：requestAnimationFrame 合并移动事件，原图和已提交绘制使用缓存层，画笔采用增量绘制/点简化；交互预览降采样，保存时再按原分辨率合成。需浏览器真机压测确认实际改善。

### C5 · P3 · 待办计时器尚未触发时，立即保存会写盘两次【已复现】

位置：`src/composables/useBoardPersistence.ts:118`、`src/composables/useBoardPersistence.ts:121`。

外层 `persistNow` 清除 text timer 后调用 `flushTodoSave`，后者因 todo timer 尚在而再次进入 `persistPendingText → persistNow`。内层完整保存结束后，外层继续再保存一次。

探针执行 `bumpTextGeneration → scheduleTodoSave → persistNow`，确认主状态键的 `setItem` 被调用两次。每次包含全板序列化、读取规范化、版本推进和广播，F2 场景下重复保存还能立即放大陈旧状态覆盖。

建议：区分“取消待办计时器”和“冲刷待办编辑”，立即全量保存前只取消计时器，成功后统一更新基线。

### C6 · P2 · 手机速记每次请求新建后台线程，没有并发上限【代码推导】

位置：`server/app.py:54`、`server/app.py:340`。

手机多行发送虽然逐条请求，但服务端马上返回成功，之前的润色线程仍在运行，因此多行可以快速启动大量并行线程和模型请求。没有线程池、任务队列、队列容量或背压。多人/多行速记叠加模型慢响应时，连接、内存和线程数会随在途请求增长。

建议：有界工作池和持久化队列，对正在处理的任务设限；关闭润色的请求先同步可靠入库，不占润色线程。与 F4 一起设计可靠接收和处理中状态。

## 建议修复顺序与补充回归

1. 先修 F1、F2、F7 和 C5：同属本地保存/同步事务，避免内容覆盖、保存假状态与重入；加入两个标签、异步读取期间输入、逆序完成和配额失败回归。
2. 修 F3、F4、F5、C6：联合调整收件箱可靠投递协议；测试响应丢失、服务重启、DB 写失败、重复请求、相同时间戳和乱序提交，验证不丢、不重复。
3. 修 F6、C2、C3：统一撤销历史和图片载荷生命周期；测试五秒后撤销、连续 100 次图片替换、历史淘汰和大图清理。
4. 修 F8：为异步操作绑定稳定工作空间；测试上传期间切换、连续快速切换、目标删除与重复任务 ID。
5. 最后优化 C1、C4：按真实使用规模准备数据集，用浏览器性能录制衡量输入延迟、长任务、内存与画笔帧率。

现有测试通过说明已覆盖的正常流程稳定，但不能排除这些竞态、故障和规模边界。本次没有把提醒权限、五秒宽限等明确的产品选择直接判为错误；需要产品决策的部分已在对应条目中说明。
